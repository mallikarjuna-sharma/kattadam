1. PRODUCT OVERVIEW
================================================================================

Kattodam (கட்டடம்) is a construction marketplace web application focused on
western Tamil Nadu, India — primarily Coimbatore and surrounding districts
(Coimbatore, Tirupur, Erode, Namakkal, Salem, Chennai).

Core business domains:
  A. Materials marketplace — cement, TMT steel, sand, bricks, paint, tiles,
     electrical, plumbing, etc. Customers browse catalog, filter by district/
     area, and submit enquiries to dealers.
  B. Kattadam Experts — builders, architects, civil engineers (currently mock
     data on customer site; admin can add experts to DynamoDB).
  C. Real estate — buy/sell/rent property listings (live API + mock fallback).
  D. Home services — plumbers, electricians, painters, etc. (mock on customer
     site; admin can add providers to DynamoDB).
  E. Admin dashboard — manage users, dealers, materials, enquiries, properties,
     experts, home services, reviews, zones, notifications, activity/sessions.
  F. KD360 partner integration — call button, chat enquiry widget, expert popup
     with phone 9944994103 (see lib/kd360-contact.ts).

User roles (UserRole type):
  - customer         — end user browsing and enquiring
  - dealer           — material shop partner (registration pending approval)
  - service_provider — home service partner
  - super_admin      — full admin access (Lambda role; routes to /admin on login)
  - staff_admin      — staff admin (Lambda role; routes to /admin on login)

IMPORTANT NOTE — README IS OUTDATED:

    + DynamoDB single-table store

2. HIGH-LEVEL TECHNICAL ARCHITECTURE
================================================================================

Architecture style: Monorepo with Next.js App Router frontend and separate
AWS Lambda backend, connected via HTTP.

Layers:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │ BROWSER (Customer + Admin UI)                                           │
  │   React 18 client components + Next.js 14 Server Components/Actions   │
  └───────────────────────────────┬─────────────────────────────────────────┘
                                  │
          ┌───────────────────────┼───────────────────────┐
          │                       │                       │
          ▼                       ▼                       ▼
  ┌───────────────┐    ┌─────────────────┐    ┌─────────────────────┐
  │ /api/* routes │    │ Server Actions  │    │ Server Components   │
  │ (Route        │    │ app/admin/      │    │ app/admin/* pages   │
  │  Handlers)    │    │ actions.ts      │    │ fetch via data-layer│
  └───────┬───────┘    └────────┬────────┘    └──────────┬──────────┘
          │                     │                         │
          │ lib/lambda-proxy  │ @kattadam/data-layer/   │
          │ forwardToKattadam │ server                  │
          │ Api()             │                         │
          └─────────────────────┼───────────────────────┘
                                │
                                ▼
          ┌─────────────────────────────────────────────────┐
          │ AWS Lambda Function URL                         │
          │ backend/lambda/src/handler.mjs                  │
          │ backend/lambda/src/router.mjs                   │
          │ Env: TABLE_NAME, KATTADAM_API_SECRET, SES, etc. │
          └─────────────────────┬───────────────────────────┘
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
          ┌─────────────────┐    ┌─────────────────┐
          │ DynamoDB        │    │ AWS SES         │
          │ kattadam-main   │    │ OTP emails      │
          │ (ap-south-1)    │    │                 │
          └─────────────────┘    └─────────────────┘

Dev-only fallback:
  When KATTADAM_API_URL is missing or API fails in development, enquiries are
  stored in .data/enquiries.json via packages/data-layer/src/internal/
  local-enquiry-store.ts

Static fallback:
  lib/mock-data.ts provides districts, areas, categories, and sample listings
  for builders, services, dealers (partial), and properties (partial).

No Next.js middleware.ts exists. Route protection is client-side only.

3. REQUEST / DATA FLOW DIAGRAMS
================================================================================

3.1 Customer catalog fetch (materials example)
──────────────────────────────────────────────
  Browser: app/materials/page.tsx
    → useEffect fetch("/api/catalog/materials")
      → app/api/catalog/materials/route.ts
        → lib/lambda-proxy.ts forwardToKattadamApi("/catalog/materials")
          → Lambda GET /catalog/materials
            → router.mjs listEntity("material", mapMaterial)
              → dynamo.mjs queryPk("ENTITY#material")
    → Client filters by district, area, category using lib/location-filters.ts
    → Category labels from lib/mock-data.ts MATERIAL_CATEGORIES

3.2 Customer enquiry submission
────────────────────────────────
  Browser: components/ui/EnquiryModal.tsx or ChatEnquiryWidget.tsx
    → lib/enquiries-api.ts submitEnquiry(payload)
      → POST /api/enquiries
        → app/api/enquiries/route.ts
          → forwardToKattadamApi("/enquiries")
            → Lambda POST /enquiries
              → DynamoDB putItem ENTITY#enquiry / ENQUIRY#<uuid>
  Dev fallback: packages/data-layer appendLocalEnquiry() → .data/enquiries.json

3.3 Customer registration
─────────────────────────
  Browser: app/auth/login/page.tsx
    → POST /api/auth/otp/send { email, purpose: "signup" }
      → Lambda /auth/otp/send → SES email with 6-digit OTP (10 min expiry)
    → POST /api/auth/register { mode, name, email, password, otp }
      → Lambda /auth/register → verify OTP → createUser() in DynamoDB
    → Auto-login: stores kattadam_session_id + kattadam_user in localStorage
    → Redirect: /home (customer) or /admin (super_admin/staff_admin)

3.4 Admin dashboard read (Server Component)
──────────────────────────────────────────
  Browser: app/admin/page.tsx (Server Component)
    → import { adminGetDashboard } from "@kattadam/data-layer/server"
      → getServerBackend() → createBackendFromEnv()
        → HttpApiBackend (packages/data-layer/src/internal/http-api-backend.ts)
          → GET Lambda /admin/dashboard
            → Header: x-kattadam-internal: <KATTADAM_API_SECRET>
            → DynamoDB aggregations

3.5 Admin mutation (Server Action)
──────────────────────────────────
  Browser: components/admin/AddDealerForm.tsx
    → <form action={actionUpsertDealer}>
      → app/admin/actions.ts actionUpsertDealer(formData)
        → adminUpsertDealer() from @kattadam/data-layer/server
          → HttpApiBackend POST /admin/dealers
            → Lambda upsertDealer() → DynamoDB
        → revalidatePath("/admin/dealers")

3.6 Session keepalive
─────────────────────
  AppShell SessionPing component (every 60s):
    localStorage kattadam_session_id
      → POST /api/session/ping { sessionId }
        → Lambda /session/ping → update SESSION#<id> lastActiveAt

8. AWS LAMBDA BACKEND
================================================================================

Entry: backend/lambda/src/handler.mjs
  - Parses HTTP method, path, headers, body, query string
  - Handles OPTIONS (CORS preflight)
  - Delegates to routeRequest() in router.mjs
  - Returns JSON response with CORS headers (origin: *)

13. AUTHENTICATION & SESSION MANAGEMENT
================================================================================

13.1 Customer auth (Lambda-backed)
──────────────────────────────────
  UI: app/auth/login/page.tsx
  Tabs: signin | register | partner

  Sign in flow:
    1. POST /api/auth/login { email, password }
    2. Lambda verifies PBKDF2 password hash
    3. Creates DynamoDB session (SESSION#<id>)
    4. Client stores:
       localStorage kattadam_session_id = sessionId
       localStorage kattadam_user = JSON.stringify(user)
    5. Redirect: super_admin/staff_admin → /admin, else → /home

  Register flow:
    1. POST /api/auth/otp/send { email, purpose: "signup" }
    2. User receives 6-digit OTP email (10 min expiry)
    3. POST /api/auth/register { mode, name, email, password, otp }
    4. Lambda verifies OTP, creates user
       mode "user" → role customer, status active
       mode "partner" → role dealer, status pending
    5. Auto-login (same as sign in)

  Session keepalive:
    AppShell → SessionPing → POST /api/session/ping every 60 seconds

13.2 Admin auth (SEPARATE — client-only, NOT Lambda)
────────────────────────────────────────────────────
  UI: app/admin/login/page.tsx
  Gate: components/admin/AdminLayoutShell.tsx
  Logic: lib/admin-auth-client.ts

  Credentials (hardcoded):
    Username: kattadam
    Password: Kattadam#123

  Storage: localStorage kattadam_admin_session_v1 = "1"

  WARNING: This is NOT server-secured. Admin pages fetch data via data-layer
  which uses KATTADAM_API_SECRET to call Lambda, but the /admin/* UI routes
  themselves are only protected by client-side localStorage check.

  NOTE: Customer login with super_admin/staff_admin Lambda role also routes
  to /admin, but still requires the separate admin localStorage gate unless
  AdminLayoutShell is bypassed.

13.3 Lambda internal auth
─────────────────────────
  When KATTADAM_API_SECRET is set on Lambda:
    All /admin/* routes require header x-kattadam-internal: <secret>
    Internal /auth/* routes also require this header
  When secret is NOT set: requireInternal() returns true (open admin API)

19. STATE MANAGEMENT & CLIENT STORAGE KEYS
================================================================================

No global state library. All state is local React useState or Context.

localStorage keys:
  kattadam_session_id       — Lambda session UUID (customer auth)
  kattadam_user             — JSON string of { id, name, email, role }
  kattadam_admin_session_v1 — "1" when admin client gate passed
  kattadam_lang             — "en" | "ta" (language preference)
  kattadam_expert_popup_minutes — popup timing config
  kattadam_expert_popup_shown   — popup shown flag

React Context:
  LangContext in AppShell.tsx — useSiteLang() returns { lang, setLang, t }

Server data:
  Admin pages use Server Components → direct data-layer calls (no client cache)
  Customer catalog pages use client-side fetch in useEffect

Theme:
  next-themes via ThemeProvider — class-based dark mode on <html>

23. COMMON IMPLEMENTATION PATTERNS
================================================================================

23.1 Next.js API route handler pattern
──────────────────────────────────────
  // app/api/<resource>/route.ts
  import { forwardToKattadamApi, lambdaPathFromApiRoute } from "@/lib/lambda-proxy";
  import { NextResponse } from "next/server";

  export async function GET(req: Request) {
    const proxied = await forwardToKattadamApi("/catalog/materials", req);
    if (!proxied) {
      return NextResponse.json({ ok: false, error: "API not configured" }, { status: 503 });
    }
    return proxied;
  }

23.2 Admin Server Action pattern
────────────────────────────────
  // app/admin/actions.ts
  "use server";
  import { revalidatePath } from "next/cache";
  import { adminUpsertDealer } from "@kattadam/data-layer/server";

  export async function actionUpsertDealer(formData: FormData) {
    await adminUpsertDealer({ shopName: String(formData.get("shopName")) });
    revalidatePath("/admin/dealers");
  }

23.3 Admin Server Component pattern
───────────────────────────────────
  // app/admin/dealers/page.tsx
  import { adminListDealers } from "@kattadam/data-layer/server";

  export default async function DealersPage() {
    const dealers = await adminListDealers();
    // render table...
  }

23.4 Client catalog fetch pattern
─────────────────────────────────
  // app/materials/page.tsx
  useEffect(() => {
    fetch("/api/catalog/materials")
      .then(r => r.json())
      .then(data => setMaterials(data.materials ?? []));
  }, []);

23.5 DynamoDB entity insert pattern (Lambda)
────────────────────────────────────────────
  const id = randomUUID();
  const item = {
    PK: entityPk("material"),       // "ENTITY#material"
    SK: itemSk("MATERIAL", id),     // "MATERIAL#<uuid>"
    id, name, category, ..., createdAt: nowIso(),
  };
  await putItem(item);

───────────────────────────────
  const payload = buildCreateEnquiryPayload(formValues, { target: "Cement enquiry" });
  const result = await submitEnquiry(payload);

24. KNOWN GAPS, RISKS & PRODUCTION CONCERNS
================================================================================

1. ADMIN AUTH IS CLIENT-ONLY
   - Hardcoded credentials in lib/admin-auth-client.ts
   - Only localStorage gate, no server session
   - MUST be replaced with proper server auth before production

2. README IS STALE
   - Claims frontend-only, no env vars, port 3000
   - Actual: Lambda + DynamoDB, requires KATTADAM_API_URL, port 3001

3. DUAL AUTH SYSTEMS
   - Customer: Lambda sessions (kattadam_session_id)
   - Admin UI: separate localStorage gate (kattadam_admin_session_v1)
   - Not integrated

4. NO TESTS
   - Zero unit, integration, or E2E tests
   - No test runner in dependencies

5. NO NEXT.JS MIDDLEWARE
   - No middleware.ts for route protection
   - /admin routes accessible if client gate is bypassed

6. CORS ALLOWS ALL ORIGINS
   - Lambda http.mjs sets Access-Control-Allow-Origin: *

7. MIXED MOCK AND LIVE DATA
   - /builders and /services use mock data only
   - /materials and /properties use live API
   - Admin can add experts/services to DB but customer pages don't fetch them

8. KATTADAM_API_SECRET OPTIONAL
   - When not set, Lambda admin API is open to anyone with the URL

9. NO RATE LIMITING
   - OTP send endpoint has no rate limiting beyond OTP attempt counter

10. NO PAYMENT INTEGRATION
    - Enquiries only, no order/payment flow

25. GLOSSARY
================================================================================

Kattadam (கட்டடம்)  — "Building" in Tamil; the brand name
KD360               — Partner logistics/delivery brand integrated in UI
Data Layer          — @kattadam/data-layer workspace package; abstraction over Lambda
Function URL        — AWS Lambda HTTP endpoint (no API Gateway needed)
Single-table design — DynamoDB pattern: all entities in one table with PK/SK
GSI1                — Global Secondary Index for email-based user lookup
Server Action       — Next.js "use server" functions for form mutations
Server Component    — React component that runs on server, can await data
Route Handler       — Next.js app/api/*/route.ts API endpoint
PBKDF2              — Password hashing algorithm (120k iterations, SHA-256)
OTP                 — One-Time Password sent via SES email for registration
Enquiry             — Customer request for quote/info on material or service
Dealer              — Material shop partner on the platform
Entity PK           — DynamoDB partition key pattern ENTITY#<type>
ListingPageShell    — Shared layout wrapper for catalog listing pages
mock-data.ts        — Static fallback data for locations, categories, samples
revalidatePath      — Next.js cache invalidation after Server Action mutation
